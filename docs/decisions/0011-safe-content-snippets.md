# 0011 — Store bounded source text for safe search snippets

## Context

Content-only results need enough surrounding text to explain why they matched. Lucene postings identify matching terms but cannot reconstruct the original human-readable passage. Reading and parsing source files again during every search would add latency, repeat exposure to malformed input, and make results depend on files that may have changed or disappeared.

## Decision

Advance the Lucene schema to version 3 and store the already extraction-bounded text in a dedicated `snippetSource` field alongside the non-stored searchable content field. The extraction character limit, 500,000 characters by default, is the upper bound per successful document. Only content-match results use this source.

Normalize snippet whitespace and select a window around the earliest matching query term. Limit the body to 240 UTF-16 characters, preserving surrogate-pair boundaries, and add ellipses when context is omitted. Return the excerpt as plain text with validated, ordered, non-overlapping UTF-16 start/end offsets for matching terms.

Map these values to explicit API DTOs. Render text and highlighted segments as React nodes and never accept or create document-derived HTML markup. Omit snippets from filename/path matches and when no safe matching range exists.

## Alternatives considered

- Return markup generated by a highlighter: rejected because plain text plus offsets creates a narrower, framework-escaped UI boundary.
- Parse the original document during search: rejected because searching must remain fast and isolated from parser/file availability.
- Store only the beginning of each document: rejected because content terms later in the extracted text would have no explanatory context.
- Return the complete stored text to the browser: rejected because the UI needs only a small matching excerpt and document contents are sensitive.

## Consequences

Every content-only result can provide durable context for any indexed term within the extraction limit. Snippet generation scans only a bounded stored value and responses remain small. The local index is larger and contains a retrievable extracted-text copy, so privacy documentation treats the entire data directory as sensitive and does not claim encryption. Earlier schema versions require a rebuild.
